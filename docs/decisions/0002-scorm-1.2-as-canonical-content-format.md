# ADR-0002 — SCORM 1.2 as the canonical content format

- **Status:** Accepted
- **Date:** 2026-06-03
- **Sprint:** SPRINT-ZEPHYRA-LMS-0 (`specs/008-zephyra-lms-foundation`)

## Context

The LMS delivers courses produced by an upstream AI-driven content provider
("CAMPUS"). The platform does not author course content itself; it ingests,
serves, and tracks whatever the provider exports. The format the provider emits
therefore dictates the format the platform must support as its canonical input.

CAMPUS exports its courses as **SCORM 1.2 packages** (a ZIP containing an
`imsmanifest.xml` at the package root plus the HTML/JS/CSS/media assets of the
shareable content objects). SCORM 1.2 is the long-standing, widely supported
e-learning interoperability standard; its runtime API (`LMSInitialize`,
`LMSGetValue`, `LMSSetValue`, `LMSCommit`, `LMSFinish`) is well understood and is
implemented client-side by the `scorm-again` library.

Candidate alternatives — SCORM 2004, xAPI (Tin Can), cmi5 — offer richer
tracking models, but none of them is what the provider ships, and adopting them
would require either a conversion pipeline or provider changes outside our
control.

## Decision

**Adopt SCORM 1.2 as the canonical content format of the platform.** Course
ingestion, storage, the in-browser player, and progress/score tracking are all
built against the SCORM 1.2 model. The runtime is bridged by `scorm-again`, which
exposes a `window.API` shim that the provider's content discovers by walking
`window.parent` (see `specs/008-zephyra-lms-foundation/quickstart.md` §3.3 and
`scorm-coverage.md`).

The CMI element coverage for Sprint 0 (which elements move the
`lmsEnrollments` aggregate vs. which are only logged to the append-only
`lmsScormEvents` trail) is documented in
`specs/008-zephyra-lms-foundation/scorm-coverage.md`.

## Rationale

1. **It is what the provider ships.** Choosing the provider's native export
   eliminates a conversion step and the fidelity risk that comes with it.
2. **Mature, well-supported runtime.** SCORM 1.2 and its API are stable and
   implemented by `scorm-again`, so the platform does not have to author a
   runtime from scratch.
3. **The Sprint 0 spike validated it end-to-end** against a real CAMPUS package:
   the provider's content found our `window.API`, and `LMSSetValue` calls for
   `cmi.core.lesson_status` and `cmi.core.score.raw` landed in Convex and
   projected onto `lmsEnrollments`.

## Consequences

- **Positive:** no conversion pipeline; a proven, off-the-shelf runtime; direct
  compatibility with everything CAMPUS produces.
- **Limitation:** SCORM 1.2 has a narrower tracking vocabulary than SCORM 2004 /
  xAPI / cmi5 (e.g., coarser status model, no statement-level analytics). This is
  accepted for V1; richer analytics are out of scope.
- **Future option:** if a later content source or analytics need requires it,
  xAPI/cmi5 support could be added alongside SCORM 1.2 without displacing it —
  this ADR does not preclude that, it only fixes the V1 canonical format.
